Anatomy of a Fake OneDrive Sync Script

How a 316 KB file called onedrive-sync.ps1 turned out to be half of a credential-theft toolkit — found after a friend's Telegram account was stolen.

A friend of mine got his Telegram account taken over. Cloud password, 2FA, all of it — didn't matter. A few days earlier he'd installed some browser extensions he probably shouldn't have. His PC was already offline by the time I got involved, but he'd pulled a file off it first: onedrive-sync.ps1, sitting quietly next to his real OneDrive sync folder, 316 KB of PowerShell that had no business being that large.

This is the story of pulling that file apart — from a first hash lookup to a fully reconstructed attack chain, and eventually to discovering it wasn't even a one-off, but one build in a campaign that had been running for months.

Note

Everything below happened in an isolated, network-cut VM with a snapshot before every execution. If you're following along with your own sample, don't skip that part — the file turned out to have a working remote-memory-patch capability, and you do not want to find that out the hard way on your host machine.

First contact: what are we even looking at?

Rule one with an unknown script: you hash it before you open it, and you never double-click it.

powershell
Get-FileHash -Algorithm SHA256 .\onedrive-sync.ps1 | Format-List
Get-FileHash -Algorithm MD5    .\onedrive-sync.ps1 | Format-List

SHA256 came back 8ff85f1b..., and — first surprise — VirusTotal had never seen it before. First Submission was today. That alone tells you something: either this is a genuinely brand-new tool, or, far more common these days, it's a per-victim build — a loader that gets recompiled fresh for every target so the hash never repeats and hash-based detection never gets a chance to catch up.

The file size backed that up. A OneDrive sync helper does not need 316 KB. Something is embedded in there.

VirusTotal's verdict was underwhelming on paper: 12 out of 75 engines, and the ones that did flag it weren't exactly confident about it:

VendorVerdict
Arcabit, BitDefender, eScan, Emsisoft, GData, VIPRECMD:Heur.BZC.PZQ.Pantera.332.5AD52FA3
ESET-NOD32 / FortinetPowerShell/Agent.EKY(!tr)
VaristPSH/Agent.AMW

Worth noticing: the six "Pantera" hits aren't six independent detections — they're all licensees of the same Bitdefender engine, so that's really one heuristic firing six times under different logos. And the vendors with proper behavioral/cloud engines — Kaspersky, Defender, Sophos, CrowdStrike — said nothing at all. Not because the file is clean, but because VirusTotal's static scan can't see what only shows up at runtime. That gap is exactly where this investigation had to go next.

Cracking open the obfuscation

Static analysis rule: read it, don't run it. I did this from Linux specifically, so there was no risk of a stray double-click executing anything.

bash
wc -l onedrive-sync.ps1   # 1859 lines — not one giant blob, mostly normal-length lines
head -c 500 onedrive-sync.ps1

The first 500 characters were already a taste of what I was in for:

powershell
$zVs3iOtGYUuxUaeLH = ("ApLBPHXOa8DLGlobal\explorIUJaegn5rJ71EnheuK0rUWVIuB4CHiw7WUwq5S7ZQTFClskwWnE9z5QwbQ"
  .TrimEnd("ZQTFClskwWnE9z5QwbQ")
  .TrimEnd("uK0rUWVIuB4CHiw7WUwq5S7")
  .Replace("IUJaegn5rJ71En", "er_wiW4YdodVUKKc2BL_thumbcac")
  .Replace((...-split "XkkcDnBUqDkXF")[(9010+1062)/8-2101-2325+3170], "de")
  .TrimStart("ApLBPHXOa8DL"));

Peel that apart by hand and you get Global\explorer_wide_thumbcache — a mutex name deliberately styled to look like a legitimate Windows Explorer/thumbnail-cache component. Its only job: make sure only one copy of this thing runs at a time, while blending in if someone's poking around in Process Explorer.

That single line was already a catalog of the obfuscation techniques running through the whole file:

TechniqueWhat it buys the author
Junk separators + -split + arithmetic indexinghides which string gets picked from an array
TrimStart/TrimEnd on a character set, not an exact substringstrips junk wrappers around the real string

Randomized variable namesdefeats human pattern-matching

The DllImport that wasn't there

Naturally, the first thing I grepped for was DllImport — the standard way PowerShell imports Win32 API functions. Zero hits. Tempting to conclude "no WinAPI usage here." Wrong conclusion.

powershell
$eSM0Ep3Ihjsg = oYMwF6bIdGrGV7Wsrq46 @([IntPtr]) ([bool])
$jYAlIJHGVQraKgxcwdaSK = MXVn2GqrFSCSZqSi8 ("...kernel32...") ("...CloseHandle...")
$fOjy80wmLc = [System.Runtime.InteropServices.Marshal]::$Km0HsrznVd($jYAlIJHGVQraKgxcwdaSK, $eSM0Ep3Ihjsg)

That's GetProcAddress + Marshal.GetDelegateForFunctionPointer — resolving Win32 functions through a raw function pointer at runtime instead of declaring them up front. Why bother? Because DllImport leaves a literal string in the binary that a signature scanner, a YARA rule, or a plain strings pass can catch. Do it via reflection instead, and there's no static import table to flag — which incidentally explains exactly why the big AV vendors stayed silent on the static scan above.

Plot twist: my own grep lied to me

With that pattern confirmed, I ran a broader sweep for the classic process-injection API family: OpenProcess, ReadProcessMemory, WriteProcessMemory, CreateRemoteThread, NtCreateThreadEx. All five: nothing. So I wrote down a working conclusion — no process injection here, this is probably self-patching only (FindPattern + VirtualProtect, likely an AMSI bypass) — and moved on.

It was wrong, and the reason it was wrong is worth remembering for any obfuscated sample: the obfuscator doesn't just scramble names, it splits them down the middle. "Open" and "Process" get built as two separate string fragments and concatenated only at runtime. An exact grep for "OpenProcess" will never match, no matter how carefully you write the regex, because that literal substring never exists anywhere in the file at once.

Once I grepped for the halves instead:

powershell
$rU7MFdOByrkHA9DYzz = MXVn2GqrFSCSZqSi8 ("...kernel32.dll...") ("...ProcessMemory...")
$IQk7wwSnJtYui4SonB = MXVn2GqrFSCSZqSi8 ("...kernel32.dll...") ("...OpenProcess...")

There it was. OpenProcess, and a function with the classic (IntPtr, IntPtr, byte[], Int32, ref UInt32) → Bool signature — which, annoyingly, is nearly identical for both ReadProcessMemory and WriteProcessMemory, so at this point I genuinely couldn't tell which one it was from the signature alone.

Correction

With this kind of obfuscation, an exact-string grep returning zero hits is not evidence of absence. Only positive hits are trustworthy. I'd find out later — see the Script Tracer breakthrough below — that both functions were actually present.

A server nobody asked for

Then came the finding that reframed the whole file. Buried in the code, a System.Net.HttpListener bound to http://127.0.0.1:58172/. Not a downloader. Not an outbound C2 beacon. A local HTTP server, bound to localhost only, with CORS headers configured on the response:

powershell
$Response.Headers.Add("Access-Control-Allow-Headers", "Content-Type")

CORS headers only matter to a browser enforcing cross-origin rules against JavaScript running on an actual web page. That's the tell: something running inside a browser tab is calling fetch() against 127.0.0.1:58172. And that only makes sense if there's a browser extension — a content script — that this .ps1 file was built to talk to.

Suddenly the whole shape of the file made sense. onedrive-sync.ps1 isn't the malware. It's half of the malware — the native backend of a toolkit whose other half, a browser extension, was never recovered. The extension reads session data straight out of an open tab (very plausibly web.telegram.org, given what actually happened to my friend) and hands it to this local server, which — theory, at this point — relays it onward. A stolen web session explains the 2FA bypass perfectly: you don't need the password or the second factor if you just take the already-authenticated session.

One more piece confirmed the "half a toolkit" read directly: the file also uses Add-Type to compile a small C# helper on the fly:

csharp
public class W32API {
    [DllImport("user32.dll")]
    public static extern bool EnumWindows(EnumWindowsProc enumProc, IntPtr lParam);
    public static List<int> FindPattern(byte[] data, byte[] pattern, bool[] mask, int patternLength) { ... }
}

EnumWindows to find a target window, FindPattern to scan for a byte signature inside a process's memory. Two tools that only make sense once you already have a target — and the only place a target PID could come from was that same local HTTP endpoint. Backend and extension, waiting on each other.

Letting it run

Static analysis gets you a long way, but at some point you have to actually flip the switch — carefully, in a disposable VM, with logging on before the first keystroke.

Run #1: ANY.RUN, and a crash

The process tree confirmed the C# compilation was real, not just theoretical:

powershell.exe -ep bypass onedrive-sync.ps1
 ├─ csc.exe /noconfig /fullpaths @a04muimf.cmdline ← compiling our W32API class
 │   └─ cvtres.exe
 └─ slui.exe -Embedding

Good — that lines up exactly with the Add-Type block found in static analysis. I pulled the compiled a04muimf.dll open in dnSpy to decompile it back to C# — worth doing any time Add-Type shows up, since it's a two-minute way to confirm a static read instead of just trusting your own manual deobfuscation. It matched, byte for byte: the W32API class, EnumWindows, FindPattern, nothing extra hiding inside.

But then the malware's own native capabilities never got a chance to run: the WinAPI resolver crashed on its very first call, and the failure cascaded through everything downstream of it — CreateWindowEx, ShowWindow, DestroyWindow, and almost certainly the memory-patch chain too, since it leans on the same resolver.

Two competing explanations, and I want to be honest that I didn't fully resolve which one was right: an honest bug — reflection-based P/Invoke via raw function pointers is fragile, and a 32-bit/64-bit pointer-size mismatch is a classic way to make it fall over — or an anti-sandbox side effect, where a fallback code path taken once the malware suspects it's being watched turns out to be the less-tested one. The errors looked like plain, uncaught .NET exceptions, which leans toward "bug" — a well-built evasion mechanism usually fails silently. But I wasn't ready to close the book on it, because…

Run #2: VirusTotal's sandbox fills in the picture

The mutex construction I'd worked out by hand matched exactly: Global\explorer_wide_thumbcache. Nice to have that confirmed byte-for-byte. But the real payoff was the highlighted API calls:

virustotal · behavior tab
IsDebuggerPresent, GetTickCount, Sleep, GetAdaptersAddresses, GetSystemMetrics
Window title check: "Administrator: c:/windows/.../powershell.exe"

That's a full anti-analysis checklist: a debugger check, a timing check (sandboxes often hook Sleep and speed it up, which a GetTickCount comparison catches), a screen-resolution check (VMs often report suspiciously generic resolutions), a network-adapter enumeration (virtual NIC names are a giveaway), and — my favorite — a check for the literal string "Administrator: " in the console window title. Windows adds that prefix automatically whenever a process runs elevated, and a lot of automated sandboxes default to running everything as admin. A normal user mostly doesn't. Check the title, and you've got a cheap, effective sandbox fingerprint.

That finding retroactively made the Run #1 crash more interesting: it wasn't proof of anti-sandbox behavior, but it made the theory more plausible than it had been an hour earlier.

Run #3: my own VM, and finally — it just works

Third time, on my own local VirtualBox VM, network isolated to host-only, running under a non-elevated console — Sysinternals' Procmon and Process Explorer watching the process tree, and FakeNet-NG standing in for the internet so anything the malware tried to reach would resolve to a fake address instead of just timing out silently. This run didn't crash.

shell
curl.exe 127.0.0.1:58172/       → {"error":"Unknown route","success":false}

A real JSON API, responding exactly where the static base-URL calculation had said it would be. Small, satisfying confirmation. And it lined up with a pattern across all three runs so far:

Run"Administrator:" in title?Result
My own VM (non-elevated)No✅ Ran cleanly, server responded
ANY.RUN (default sandbox user)Yes❌ Resolver crashed
API Monitor (forced elevation)Yes❌ Crashed again

Three independent data points, same correlation each time. Not proof, but a pattern too clean to ignore.

With FakeNet-NG faking DNS, I filtered the capture in Wireshark and watched a handful of lookups go by — ctldl.windowsupdate.com, config.edge.skype.com, self.events.data.microsoft.com — all routine Windows background noise, all resolved to FakeNet-NG's placeholder address, and not one followed by an actual TLS handshake. Combined with the identical null result from ANY.RUN and VirusTotal's sandbox, that's three independent environments agreeing: nothing in this file talks to the outside world on its own.

A brief, frustrating detour with API Monitor

I wanted call-level visibility into the WinAPI resolver, so I reached for API Monitor. Two attempts, two failures — and neither one was the malware's fault. The first run used the wrong architecture build entirely (32-bit monitor against a 64-bit process). The second, correctly matched to 64-bit, still died — but this time inside the plain .NET/CLR bootstrap, before the obfuscated script even started executing. Manual API-hooking tools and managed .NET code apparently don't get along. Lesson filed away, tool retired for this sample.

The breakthrough: letting the sandbox do the deobfuscation for me

This is the part of the investigation I'd point to if someone asked "what actually cracked this open." ANY.RUN has a feature called Script Tracer that logs every single .Replace(), .Substring(), .TrimEnd() call the script makes at runtime, with real before/after values. It is, functionally, automated manual deobfuscation — the exact tedious work from the static-analysis section above, done instantly and completely by the sandbox instead of by hand.

It confirmed the mutex construction down to the character. And it settled, once and for all, the question that had been nagging since the very first grep:

script tracer · resolved calls
MXVn2GqrFSCSZqSi8 kernel32.dll OpenProcess
MXVn2GqrFSCSZqSi8 kernel32.dll ReadProcessMemory
MXVn2GqrFSCSZqSi8 kernel32.dll WriteProcessMemory
MXVn2GqrFSCSZqSi8 kernel32.dll VirtualProtectEx
MXVn2GqrFSCSZqSi8 kernel32.dll CloseHandle

Not "read or write" — both. Combined, that's a complete call chain:

OpenProcess → get a handle on the target process
ReadProcessMemory → read its memory (e.g. locate a FindPattern target)
WriteProcessMemory → write into its memory — an actual patch
VirtualProtectEx → flip memory protection before writing
CloseHandle → clean up
Breakthrough

That's not passive reading and it's not just self-patching. That's a complete remote memory-patch primitive against a process addressed by PID — MITRE calls this Process Injection (T1055), and it's a meaningfully more dangerous capability than my early "probably just an AMSI bypass" read.

Two more small pieces clicked into place from the same trace: GetWindowThreadProcessId, which turns a window handle from EnumWindows into a process ID — a second, extension-independent way for the malware to find its target — and confirmation that amsi.dll is genuinely loaded in the process, which is the necessary precondition for an AMSI-bypass patch to even be possible in the first place.

Not a loner

With the file itself fully mapped, I pointed VirusTotal's Graph feature at the hash of the compiled C# helper's source (.0.cs) instead of the .ps1 hash — deliberately, because the compiled DLL's hash is useless for correlation (every build gets a fresh MVID and PE timestamp from the compiler, so it never repeats even for byte-identical source). The source file hash, by contrast, is stable.

That one pivot opened up a lot:

  • 20 "execution parents" — other samples that drop this exact same .0.cs source.
  • Some of those parents weren't named onedrive-sync.ps1 at all — hash-named files, different bait entirely. Same building block, reused across campaigns. This isn't one attacker's custom tool; it's a shared builder/toolkit.
  • A timeline stretching from 2026-04-18 to at least 2026-07-09 — nearly three and a half months of continuous activity, not an isolated incident.
  • Detection rates climbing steadily over that window: April builds sat at 0–1 out of 62–63 engines; July builds were up to 8–26 out of 60–61. Textbook AV catch-up pattern against a continuously rebuilt tool.
  • A recurring, if generic, family label: Wacatac, plus a Fortinet signature (PowerShell/Agent.EKY!tr) that stayed identical across three separate builds — evidence Fortinet is catching a structural pattern, not a specific hash.
Calibration check

VT Graph also surfaced a possible delivery archive (onedrive-sync.zip) and a low-confidence C2 domain candidate. I'm deliberately not treating either as confirmed. The ZIP is a single data point that could just as easily be an analyst's own bundling as a real distribution artifact, and it doesn't match what actually happened to my friend (browser extensions, not a downloaded archive). The domain had exactly one vendor flag out of ninety-one. Graph relationships are leads, not facts — worth writing down, not worth overclaiming.

Putting it together

Verdict

Strip away the obfuscation layers and the sandbox drama, and here's what onedrive-sync.ps1 actually is: a modular PowerShell trojan / local IPC agent. Not a downloader — no downloader cmdlets anywhere in the file, no outbound C2 traffic in three independent execution environments. It's the native backend half of a two-part toolkit.

Start to finish, it: disguises itself as a OneDrive helper and checks a disguised mutex to avoid running twice; actively checks for a debugger, a sandboxed environment, and elevated/admin context before doing anything risky; resolves every Win32 API it needs at runtime through raw function pointers, specifically to avoid leaving a static import table for scanners to catch; compiles a small native helper on the fly for window enumeration and memory-pattern scanning; runs a CORS-enabled local HTTP server as a bridge to a browser extension that was never recovered; and, once it has a target process ID, opens the process and both reads and writes its memory. A complete remote memory-patch capability, most plausibly aimed at patching amsi.dll in a browser process, confirmed loaded in the target.

My friend's actual, confirmed impact — Telegram access stolen straight through a valid, already-authenticated session, no password or 2FA needed — is exactly the outcome this architecture is built to produce.

And the VT Graph pivot means this isn't a one-off. It's one build in a toolkit that's been actively maintained and reused across different campaigns for months, with AV detection slowly catching up behind it the whole time.

Worth sitting with for a second: it's checking for the exact mechanisms I used to catch it.

What I'd do differently next time

A few habits this analysis earned the hard way:

  • An exact-string grep returning zero hits proves nothing against name-splitting obfuscation. Only positive matches are trustworthy; treat every "not found" as "not found this way."
  • Get-WinEvent needs a ProcessId filter. Script Block Logging is system-wide — without filtering, unrelated process events (I chased a false lead from Windows' own Program Compatibility Assistant) get mixed in with the sample's own.
  • Compiled-DLL hashes from Add-Type are not stable IOCs. Every csc.exe run bakes in a fresh MVID and PE timestamp, even for byte-identical source. Hash the source, not the output.
  • Manual API-hooking tools and managed .NET code don't mix well. If your hooking tool dies inside the CLR bootstrap before the target code even runs, that's the tool, not the malware.
  • A sandbox's automated Script Tracer / behavior trace can out-perform hours of manual deobfuscation. Use it as a first pass, then go back to the static file to verify.
  • Not every VT Graph edge is a fact. Execution parents and shared hashes are strong; "Collections" and multi-hop relationship chains are leads worth a footnote, not a citation.

Recommendations

For my friend, the advice was blunt: treat the machine as fully compromised, not just infected. This sample can write into another process's memory — a targeted file cleanup isn't trustworthy against that capability class.

  • Full OS reinstall — not just deleting the file.
  • Kill every active Telegram session from a clean device, then change the password.
  • Change every password that touched the affected browser, from a different device.
  • Pull the Chrome extensions list and remove anything sideloaded or unfamiliar.

The file that started this was 316 KB of PowerShell someone built to look boring. It turned out to be half of a working credential-theft toolkit, active in the wild for months, with a real victim on the other end of it. That's usually how it goes — the interesting part is never the file name.
